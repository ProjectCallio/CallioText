4. The Printer

This chapter brings the right half online: first the printer renders a hand-written tree, then we connect it to the editor, closing the loop of writing on the left and reading on the right. At the end comes a bit of the printer's inner workings, preparing for chapter 6's automatic numbering.

Step 1: let the printer render something

The printer component needs a tree to work with, and the editor's tree arrives only in the next step. So let's feed it a hand-written minimal tree first, which doubles as a review of chapter 1's node structure. Update src/App.tsx: 

import React, { useRef } from "react"
import {
    DefaultEditorComponent, DefaultPrinterComponent,
    AbstractNode,
} from "@project-callio/calliotext"
import { editor_core, printer } from "./core"

const half: React.CSSProperties = {
    position: "absolute", top: 0, height: "100%", width: "49%",
}

// A minimal hand-written tree: one root, one paragraph inside.
const hello_tree: AbstractNode = {
    type: "abstract", concept: "root", idx: "root",
    parameters: {}, abstract: [],
    children: [{children: [{text: "Hello, printer."}]}],
}

export default function App(){
    const editor_ref = useRef<DefaultEditorComponent | null>(null)

    return <div style={{position: "absolute", inset: 0}}>
        <div style={{...half, left: 0}}>
            <DefaultEditorComponent
                ref={editor_ref}
                editorcore={editor_core}
            />
        </div>
        <div style={{...half, left: "51%"}}>
            <DefaultPrinterComponent
                printer={printer}
                root={hello_tree}
            />
        </div>
    </div>
}

Check hello_tree against chapter 1: an abstract node (type: "abstract") with concept root, no parameters, no attached abstract nodes, and one paragraph holding a text node in its children. DefaultPrinterComponent asks for exactly two things: the printer (printer) and the tree to render (root).

Reload. The right half should show the typeset form of "Hello, printer." Try editing the text inside hello_tree or adding a second paragraph object; the right side follows, which proves that what the right half renders really is this tree.

Step 2: connect the editor

Now replace the hand-written tree with the real one from the editor. As chapter 1 mentioned, the editor internally uses Slate's data structures (to support cursors, selection and undo/redo), while the printer wants a plain document tree. The bridge is the editor's get_root() method: it assembles the current editing content into a complete document tree and returns it.

The plan: keep a state holding "the tree currently on display", give it to the printer; when the user saves, call get_root() for the latest tree and update the state. The revised App.tsx: 

import React, { useRef, useState, useCallback } from "react"
import {
    DefaultEditorComponent, DefaultPrinterComponent,
    AbstractNode,
} from "@project-callio/calliotext"
import { editor_core, printer } from "./core"

const half: React.CSSProperties = {
    position: "absolute", top: 0, height: "100%", width: "49%",
}

// The initial tree goes back to an empty document: one root, one empty paragraph.
const empty_tree: AbstractNode = {
    type: "abstract", concept: "root", idx: "root",
    parameters: {}, abstract: [],
    children: [{children: [{text: ""}]}],
}

export default function App(){
    const editor_ref = useRef<DefaultEditorComponent | null>(null)

    // The tree currently on display.
    const [tree, set_tree] = useState<AbstractNode>(empty_tree)

    // Pull the latest tree out of the editor and update the state.
    const refresh = useCallback(() => {
        // editor_ref.current is the DefaultEditorComponent;
        // its get_editor() returns the actual working editor inside.
        const editor = editor_ref.current?.get_editor()
        if (editor) set_tree(editor.get_root())
    }, [])

    return <div style={{position: "absolute", inset: 0}}>
        <div style={{...half, left: 0}}>
            <DefaultEditorComponent
                ref={editor_ref}
                editorcore={editor_core}
                onSave={refresh}
            />
        </div>
        <div style={{...half, left: "51%"}}>
            <DefaultPrinterComponent
                printer={printer}
                root={tree}
            />
        </div>
    </div>
}

Only two things are new. onSave={refresh}: when the user triggers the save action in the editor (the save button in the interface, or the save shortcut), DefaultEditorComponent calls the function you pass in, and our refresh pulls the latest tree into the state. The editor_ref left over from the previous chapter finds its use here.

Reload, type a few paragraphs on the left, trigger a save. The right half should show their typeset form. Change a few words, save again; the right side follows. The write-left, read-right loop is closed. The two sides still look similar, since the document holds only paragraphs and text and every renderer is the no-styling default; both sides come alive in chapter 5.

Why refresh-on-save instead of live sync?

The right side updates on save rather than on every keystroke. This is deliberate, for two reasons:

  • Every keystroke changes the tree. Re-rendering the entire document in the printer on every change will not hold up as documents grow.
  • More importantly, the printer preprocesses the whole tree before rendering (next section). That is document-wide work, not something to repeat per keystroke.

If you do want live preview, the editor also offers an onUpdate callback that fires on every tree change. Hook refresh up to it and you have live sync, at a performance cost you should weigh yourself.

The printer works in two phases

A bit of internals here; chapter 6 depends on it. When DefaultPrinterComponent receives a tree, it does not render directly. It works in two phases:

  1. Preprocessing. It walks the entire tree in document order, accumulating information along the way: which theorem this is, which figure, who references whom. When the walk finishes, every node has received a set of conclusions about itself, such as "you are the third theorem".
  2. Rendering. It walks again, this time producing the page content. Each node's rendering code can read the conclusions preprocessing left for it, and so knows to display itself as "Theorem 3".

The reason for the two phases came up in chapter 1: a theorem's number depends on how many theorems precede it, which no single node can know by itself; someone has to walk the document and count. Cross references are the same: the 3 in "see Theorem 3" exists only after counting. Chapter 6 uses this machinery to give our own concepts automatic numbers.

Chapter summary

  • DefaultPrinterComponent needs only a printer and a tree; where the tree comes from is not its concern. Hand-written or pulled from the editor both work.
  • get_root() assembles the current editing content into a document tree; with a state and onSave, that makes the refresh-on-save preview loop.
  • The printer works in two phases: preprocessing (a full walk accumulating information), then rendering. Numbering and cross references build on preprocessing.
