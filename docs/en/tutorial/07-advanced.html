7. Advanced Topics

The last chapter covers the remaining pieces between a demo and a usable application: saving and loading documents, creating second-class concepts at runtime, writing your own plugins, keyboard operation, and styling. The sections are independent; read what you need.

Saving and loading documents

The document tree is plain data that serializes straight to JSON, with no special objects inside. Saving is just taking the tree (with the method already used in chapter 4) and serializing it: 

const editor = editor_ref.current?.get_editor()
if (editor) {
    const root = editor.get_root()          // a complete document tree (AbstractNode)
    localStorage.setItem("doc", JSON.stringify(root))
}

Loading involves two extra steps. First, data of uncertain origin (user uploads, archives from older versions) should be run through the library's validate function before it reaches the editor; it recursively checks the tree's structure and reports errors with node paths. Second, the editor component receives its initial document as two pieces: the content (children) goes to init_rootchildren, and the root's remaining properties (idx, concept, parameters and so on) go to init_rootproperty: 

import { validate, AbstractNode } from "@project-callio/calliotext"

const saved = JSON.parse(localStorage.getItem("doc")!)

// Validation: when ok is false, msg explains the problem with a node path.
const [ok, msg] = validate(saved)
if (!ok) throw new Error(msg)

const {children, ...property} = saved as AbstractNode

<DefaultEditorComponent
    editorcore={editor_core}
    init_rootchildren={children}
    init_rootproperty={property}
/>

As chapter 3 noted, omitting these two props makes the editor create an empty document; providing them makes it start from yours.

Creating second-class concepts at runtime

Chapter 1 promised that second-class concepts can be created at runtime without code. Here is that promise kept. A second-class concept is fully described by a handful of fields (what it inherits, what it is called, which parameters it overrides), so it can live in a JSON file or come from a backend API. Below is the definition of a Proposition concept from a real system: 

{
    "Proposition": {
        "first": "primary",
        "type": "group",
        "fixed": {
            "title":  {"val": "p=>p.category.val", "type": "function"},
            "prefix": {"val": "p=>p.alias.val",    "type": "function"}
        },
        "default": {
            "category": {
                "val": "Proposition", "type": "string",
                "choices": ["Theorem", "Lemma", "Corollary", "Claim", "Proposition"]
            },
            "alias": {"val": "", "type": "string"}
        }
    }
}

Two new things in this definition:

  • Function-typed parameters. In fixed (which corresponds to fixed_override in code), the value of title is not a string but a piece of arrow-function code, p => p.category.val, with type function. At print time it is evaluated with the node's parameter table as p. The effect: title is no longer a fixed value but follows the category parameter automatically.
  • choices. Parameter value objects may carry extra fields, and choices is one the default parameter editor understands: a parameter with it renders as a dropdown instead of a free text input.

Together, this one second-class concept does the work of five: an author inserts a Proposition, flips category to Theorem or Lemma in the parameter panel, and the heading follows, with no need for five separate concepts.

Turning such JSON into concept objects is ordinary iteration and construction:

const ret: SecondClassConcept[] = []
for (const name in data) {
    const info = data[name]
    ret.push(new SecondClassConcept({
        name,
        type: info.type,
        first_concept: info.first,
        default_override: info.default,
        fixed_override: info.fixed,
    }))
}
// Pass them to the Printer constructor, or append dynamically
// with printer.add_second_concept(x).

Writing your own plugins

Chapter 3 mentioned that the tree's structural constraints are maintained by built-in normalization plugins. When you need constraints of your own (forcing the document to open with a certain node, for instance), you write a plugin. Its type is: 

type EditorPlugin =
    (editor: EditorComponent, slate: ReactEditor) => ReactEditor

It receives the editor and the underlying Slate editor object and returns the (usually modified) Slate editor, the standard pattern in the Slate ecosystem. The most common form wraps normalizeNode: Slate calls it after every content change to check and repair structure, and we append our own checks inside. The following plugin forces the document to begin with a divider: 

import * as Slate from "slate"
import { ReactEditor } from "slate-react"
import {
    EditorComponent, slate_is_concept, get_normalize_status,
} from "@project-callio/calliotext"

function force_leading_divider(editor: EditorComponent, slate: ReactEditor): ReactEditor {
    const normalizeNode = slate.normalizeNode

    slate.normalizeNode = (entry: [Slate.Node, number[]]) => {
        const [node, path] = entry

        // Skip checks while the document is loading. The tree passes through
        // intermediate states during loading, and repairing too eagerly there
        // can corrupt the document.
        if (get_normalize_status("initializing")) {
            normalizeNode(entry)
            return
        }

        if (path.length === 0) {   // an empty path means we are checking the root
            const root = node as Slate.Editor
            const first = root.children[0]
            // slate_is_concept checks whether a Slate node is a concept node;
            // the second argument narrows the kind.
            if (!first || !slate_is_concept(first, "support")) {
                // Constraint violated: repair. create_support makes a support node
                // by second-class concept name; add_nodes inserts it at path [0],
                // the start of the document.
                editor.add_nodes(editor.get_core().create_support("Divider"), [0])
                return   // return after repairing; Slate re-runs normalization to confirm.
            }
        }
        normalizeNode(entry)
    }
    return slate
}

Mount it through the plugin prop:

<DefaultEditorComponent editorcore={editor_core} plugin={force_leading_divider} />

Multiple plugins nest in sequence: plugin={(e, s) => pluginB(e, pluginA(e, s))}. The built-in normalization plugins always apply; yours stack on top of them rather than replacing them.

The tree operation API

The add_nodes used in the plugin above belongs to a family of tree operations the editor provides. The ones most used in plugins and custom buttons (the full list is in the API docs):

MethodPurpose

Keyboard operation

The default editor ships a complete keyboard operation scheme (built on the @ftyyy/mouseless library): Alt-based chords such as Alt+S enter a spatial navigation mode, arrow keys then move between node buttons, the sidebar and the concept area, and Enter triggers the selected button. Holding a control key for a moment reveals hints next to each button; a ShowHintControlButton component can keep the hints permanently visible. All of this comes with DefaultEditorComponent, no configuration required.

Styling

The editor and the printer each accept a style configuration covering fonts, margins and widths. The configuration is partial: specify only what you want to change, everything else keeps its default: 

<DefaultEditorComponent
    editorcore={editor_core}
    config={{fonts: {body: {fontFamily: "serif"}}}}   // type: PartialEditorConfig
/>

<DefaultPrinterComponent
    printer={printer}
    root={tree}
    config={{margins: {paragraph: "0.8rem"}}}          // type: PartialPrinterConfig
/>

Add sidebar_extras (an array of components appended to the sidebar) and onSave, and what you have matches the skeleton of the complete example application in the repository's test/demo.
